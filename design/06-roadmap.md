# 分阶段路线与决策记录

> 状态：首轮建议，2026-11-03；**2026-11-06 更新：P0–P2 已实施（`0.1.0-alpha.1`），证据见 [07-implementation-status.md](07-implementation-status.md)。** 里程碑按能力与证据验收，不在缺少团队规模和业务样本时编造开发工期。

## 1. 决策状态

| 事项 | 状态 | 本轮结论 |
| --- | --- | --- |
| 名称、语言、参考产品 | 用户已确认 | Jaunt、C#、与 MoeJS 同类 |
| 运行时矩阵 | 用户已确认 | .NET 8 / .NET 10 / .NET 11 |
| NativeAOT | **用户已确认、强制** | 每阶段正式承诺的运行时能力完整支持 AOT，发布后仍可编译/执行新 JS；不是可选基线 |
| 设计位置 | 用户已确认 | 所有设计在 `design/` |
| 纯托管内核 | 已实施 | 不将 V8/QuickJS bridge 当核心产品实现 |
| 首个执行后端 | 已实施 | 寄存器字节码解释器（显式帧栈、IC、热/冷 op 拆分） |
| 前端 | 已实施并验证 | Acornima 1.9.1 内部适配；不暴露其 AST；token 级栈/取消检查、节点预算 |
| Value 布局 | 已实施（alpha 内可调） | 16B：独立引用字段 + XOR 编码 64 位载荷 |
| 并发模型 | 已实施 | 单引擎独占、冲突 fail-fast，多引擎并行 |

| 数据与绑定 | 已实施，AOT 已验证 | 快照/生成/手写映射，不静默发码或反射回退；受控反射若交付也须 AOT 验证 |
| 运行时 JS→IL 后端 | 不纳入当前主路线 | 不作为功能/性能达标依赖；未来另行研究也不能替代 AOT 验收 |

| 性能数值 | 已有本机数据 | 见 `docs/benchmarks.md`；对 Jint 4.17.0 多数负载 1.3–4.6×，新建引擎仍慢于 Jint |
| Jaunt 许可证、发布策略 | 待项目决策 | 不擅自创建 LICENSE 或沿用竞品许可证 |

推荐方案是用于下一轮验证的起点，不代表用户已经批准每个技术细节。

## 2. P0：先验证产品成立的技术前提

**目标：用最少实现排除代价最高的错误路线；P0 不是完整 JS 引擎。**

| Spike | 验证内容 | 必须产出的证据 / 不通过时怎么办 |
| --- | --- | --- |
| P0-A 前端与 AOT | Acornima→少量自有字节码；AOT/trim；深度/长度/节点/取消 | 必须运行 NativeAOT 发布成品并提交发布后新源码，解决相关诊断；解析不可停止或依赖不能 AOT 时修正/替换方案，不能降级硬要求 |
| P0-B VM / Value | 数值、分支、函数、对象属性；常规 vs 压缩布局；dispatch | size、GC stress、反汇编和微基准；不能因追 16B 损害 GC/undefined/数值语义 |
| P0-C 宿主数据 | 固定 arity、typed delegate、手工 DTO descriptor、JSON eager 路径 | 在 CoreCLR/NativeAOT 中完成同一输入→调用→输出及错误链；先手写静态 descriptor 验证，再自动生成，不以反射回退起步 |
| P0-D 预算边界 | root scope、输入/输出/getter、深循环、取消、状态失效 | 无预算绕过、无迟到取消污染；无法中断的宿主能力明确隔离 |
| P0-E 共享与实例 | 同一模块模板多引擎、独立 IC/全局、FreshRealm 与 buffer 回收 | 并发正确性、创建/留存/长期曲线；确认共享元数据不捕获 Realm |

P0 可从同步、strict 的小子集开始，公开标明受限范围；不得把这套微型实现包装成现代 JS 支持。还不需要完整 source generator、Web API、ESM 图和 JIT。

### P0 退出条件

- 在 .NET8/10 与 .NET11 对应通道上发布并实际运行 NativeAOT 最小宿主，保留普通 CoreCLR 对照；RC 与 GA 分开，矩阵证据不外推。
- 向发布成品提供构建时未知的 JS，完成编译、执行、宿主绑定、DTO/JSON 和预算终止的最小闭环；相关 AOT/trim 诊断逐项解决。
- P0 不要求完成全部 JS，但已声明的同步子集必须在 AOT 下完整可用，不能以“只有预编译脚本可跑”代替。
- 基准可重现，能说明主要成本在 parser、VM、interop 还是初始化。
- 没有 GC 不安全引用、未受限深递归、明显状态串扰或取消后无限后台工作。
- 对成熟托管基线存在可解释的优化空间；若没有，先调整路线，不直接进入全面标准库实现。

## 3. P1：同步执行内核与可用 alpha

交付目标：

- `JsEngine`、`JsCompiler`、`JsScript`、`JsValue`、诊断和根执行预算。
- 明确清单内的表达式、变量/TDZ、控制流、函数/闭包、对象/数组、异常/finally。
- 基础内建与正确的 JSON eager 路径，不用“调用 .NET 方法”冒充完整语义。
- Script 编译结果共享、函数调用、显式宿主函数、手工 DTO descriptor。
- Standard/Hardened 的明确入口、归属检查、故障状态、dispose 契约。
- 固定 revision 的 test262 runner、差分、fuzz 与基础 benchmark。
- 本阶段新增的每项正式能力同步进入 NativeAOT 发布后运行测试，不积累“等以后再补 AOT”的实现债务。

不是“先跑通 happy path 再补语义”：被声明支持的属性/作用域/异常路径必须一起测试。此阶段允许只覆盖部分语言，但未支持特性必须拒绝并公开，不静默当成另一种语言。

## 4. P2：插件 MVP

交付目标：

- ESM 编译/链接/实例化、导出 live binding、cycles、模块 resolver 与加载限制。
- Promise、async/await、明确的自动 pump、异步宿主绑定和 root 生命周期。
- 同步/异步模块加载与 TLA 的明确完成结果；某特性未完成时写入 feature manifest，不让 API 返回“似乎成功”的半初始化实例。
- 源生成 `JsTypeInfo<T>`、受控宿主服务绑定、禁止反射回退的诊断。
- 完整 DTO/JSON 请求调用；`JsPlugin`、FreshRealm 租约、迟到任务隔离。
- 高频使用语法和标准库逐项补齐，例如箭头函数、解构、可选链、class 的承诺子集、Map/Set、常用字符串/数组能力。
- 插件端到端 benchmark，以及三个目标框架对应通道的完整 NativeAOT 消费测试；ESM/Promise、同步异步绑定、DTO/JSON 和 Hosting 不因核心 VM 已通过就免验收。

此阶段异步先以**请求式执行**为边界，不同时实现后台驻留 event loop、手工 pump 和任意跨线程 resolver。同步入口在调用 async host delegate 前拒绝；root 成功关闭前仍有未完成的外部宿主工作时，以 `UnjoinedAsyncWork` 失败、取消并 fault 引擎，不默默后台化或无限等待。这会限制 fire-and-forget 和 Promise.race 的未结束宿主 I/O loser，必须列入兼容说明；长驻模式留到 P3。

### MVP 的“可用”定义

使用者能够：

1. 编译一个模块供多实例复用。
2. 注入少量明确授权的同步/异步宿主能力。
3. 输入 DTO 或 JSON，调用导出函数，取得普通 .NET 输出。
4. 取消或限制执行，得到来源/调用栈清晰的错误。
5. 并行执行多个隔离请求，证明无串状态。
6. 知道具体支持什么 JS、哪些能力被禁用、哪些行为有兼容限制。

以上能力在 NativeAOT 与 CoreCLR 下均须成立；不以某个 ECMAScript 年份的口号，或只可发布的空壳宿主，替代这个验收清单。

## 5. P3：覆盖、优化与工程化

根据真实插件语料与 profiling 决定顺序：

- 更完整的 class/private、generator/async iteration、Proxy/Reflect、BigInt、typed arrays、RegExp 与 Annex B 等。
- 分别定义 ECMA-262、ECMA-402、Web/Node 扩展的支持范围；完整 Intl/Temporal 不自动进入核心承诺。
- 经过差分验证的 lazy JSON、输入所有权转移、切片物化与直接输出优化。
- 缓存限额、source retention、长期 GC、组件大小和 API 可诊断性。
- 独立网络/timer/stream 扩展，默认拒绝能力，补齐超时、背压、取消与关闭协议。
- 显式长驻 session/event loop，与请求式执行区分；验证跨 root 的合法 Promise、会话预算与回收。
- 调试、source map、生成 `.d.ts`、TypeScript 外部工具链等开发体验。

Jaunt 的正式稳定版应有公共 API 兼容策略、版本化特性清单和发布门槛；不能从“测试都跳过了所以 100%”宣布标准完备。新增正式运行时扩展及其依赖同样必须满足完整 AOT 路径和发布运行验证，不能靠拆包或 AOT 专用 skip 豁免。

## 6. P4：有证据才增加 AOT 兼容的高级优化

只有 profiling 证明需求后才研究：

- 反馈驱动的字节码专门化、合并指令、有限的调用/属性快路径；使用已经编译的操作实现，不运行时发 CLR IL。
- 源生成更完整的强类型宿主适配、直接 DTO 映射和内建元数据，控制代码体积与闭合泛型膨胀。
- 固定脚本的可选构建期预编译；受控生成初始化数据、明确版本/验证边界，不顺便开放任意不可信 bytecode 入口。
- 必要时研究受限、可证明语义的构建期 JS→C# 快路径，保留正确解释器回退、guard 和预算；它不能成为执行发布后新脚本的前提。

`Jaunt.Jit` / 运行时 JS→IL 不属于当前交付主路线。未来如独立研究 CoreCLR 专用加速，必须另行决策；不能用它满足 AOT 的功能或性能验收。这不取消普通 CoreCLR 部署。

持久化 bytecode、预初始化 snapshot、多 Realm 活对象共享仍需独立 ADR、验证器和 threat model，不塞进最初 MVP。

## 7. 当前仍需验证的事项

| 问题 | 为什么重要 | 何时处理 |
| --- | --- | --- |
| 真实业务插件、输入大小与错误比例 | 决定性能目标和标准库顺序 | P0/P1 选语料；没有用户样本时先自建公开 workload |
| 稳定的默认限额数值 | 过松不安全，过严会破坏常见脚本 | P0/P1 根据基准与攻击语料冻结 |
| parser 取消与栈安全 | 不能先承诺安全，再发现解析阶段不受控 | P0-A，阻断进入不可信代码场景 |
| 最小异步关闭与未结工作契约 | 决定 Promise/host Task 是否越界与能否池化 | P2 前的状态机测试，必须先于 Async API 冻结 |
| RegExp/Unicode/Date 的实现路线 | BCL 不是自动兼容层，开发量大 | P1 做边界验证，P2/P3 按特性落实 |
| .NET8 后上游 EOL 的维护承诺 | 库兼容性与运行时安全是两件事 | 发布策略制定；不静默删除用户目标 |
| NativeAOT 实现与 RID 证据 | 是否必须支持已确定；待验证的是实际实现、依赖及各承诺组合 | P0 起持续发布/运行，缺失证据阻断对应支持声明 |
| 项目及第三方许可、发布包名 | 影响分发与代码复用，不宜默认沿用竞品选择 | 实施依赖/准备分发之前 |

这些事项不阻止完成本轮设计，但在对应门槛通过前不能对外作能力保证。

## 8. 后续设计维护约定

- 设计继续放 `design/`，事实变更时更新对应文档，避免另建一套口径。
- 重要选择记录背景、备选方案、取舍、验证结果和撤回条件。
- API 草案进入实现后，文档代码示例转成可编译消费测试；不同 TFM 的 API 差异检查进入 CI。
- 不改写历史基准来掩盖回归；记录版本、配置和语义变化。
- 未经明确决定，不把研究中看到的特性自动扩成下一阶段承诺。
