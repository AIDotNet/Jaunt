# Jaunt：产品定义与设计入口

> 状态：首轮设计草案，2026-11-03。当前仓库尚无引擎实现。本文区分用户已确认要求、推荐方案和待验证假设；示例 API 不代表已发布能力。（2026-11-06 更新：已实施为 `0.1.0-alpha.1`，实测与偏差见 [07-implementation-status.md](07-implementation-status.md)；本文保留为设计记录。）

## 1. 已确认的要求

- 项目名称：**Jaunt**。
- 使用 **C#** 构建与 [MoeJS](https://github.com/MoeForge/moejs) 同类的 JavaScript 引擎产品。
- 最终支持目标：**.NET 8、.NET 10、.NET 11**。
- **必须支持 .NET NativeAOT**：这是用户明确的硬性产品与发布要求，不是可选优化或未来尽力兼容项。
- 不再把 .NET Standard 2.0、.NET Framework 2.0 或 .NET 9 纳入承诺支持矩阵。
- 性能是核心要求；目标是适合 .NET 开发者日常使用的高性能 JS 引擎，而非只完成一个语言解释器演示。
- 先明确产品范围、架构与易用 API，所有设计资料放在 `design/`。

“支持哪些运行时”与“发布哪些 TFM 资产”不是同一问题，具体见 [框架支持策略](05-dotnet-support.md)。

## 2. 一句话定位

**面向 .NET 应用内嵌脚本、规则与插件的纯托管 JavaScript 引擎，以低边界调用成本、可共享编译结果、可控执行和良好的 C# API 为主要价值。**

“纯托管内核”是本轮建议，不是用户额外指定的技术细节：核心不依赖 V8/QuickJS 的原生桥接，但可以使用经过审查的托管解析器依赖。

不将“在所有程序上比 V8 快”作为定位。短插件调用、JSON/DTO 转换、并发实例密度，与长时间数值计算，是不同的优化问题。

## 3. 我们真正要解决什么

| 典型场景 | 宿主需要 | Jaunt 的设计重点 |
| --- | --- | --- |
| API 网关、AI 请求改写 | 输入大型 JSON，只读写少数字段，再输出 | 数据转换、懒物化、输出预算、避免无谓复制 |
| 业务规则、计价、风控条件 | 编译一次，高频调用小函数 | 预编译、函数句柄、固定参数调用、低分配 |
| 可扩展服务端插件 | 显式注入能力，调用 JS 导出函数 | ESM、宿主绑定、Promise、取消、错误诊断 |
| 桌面应用脚本 | 易接入、部署简单、脚本报错可定位 | 简洁 API、CoreCLR/NativeAOT 部署、源码位置、生成/显式绑定 |
| 多租户执行 | 并行但不能串状态，可限制滥用 | 独立 Realm、能力白名单、计费预算、必要时进程隔离 |

优先服务前三类场景。桌面便利 API 和多租户加固不应迫使所有调用走反射或支付远程进程开销。

## 4. 产品边界

以下是产品的能力边界，**不是 P0 要一次实现的列表**。首个验证面只包含一个小型同步 Script 子集、宿主函数、eager 数据转换和完整预算；模块、异步与生成绑定分阶段进入。

### 核心应包含

1. JavaScript 解析、语义分析、编译、执行和错误诊断。
2. Script 与 ES Module 两种入口；编译结果与模块执行实例分离。
3. JavaScript 对象模型、标准内建能力和明确的特性支持清单。
4. JS ↔ C# 值转换、显式宿主函数、强类型 DTO 映射。
5. Promise/job queue 的语言运行机制；任务完成回到串行执行器。
6. 可取消执行、工作量/深度/计费分配/输出限制。
7. 共享编译、诊断计数与可复现性能基准。

### 可选层，不绑进最小核心

- 引擎池、插件包装、依赖注入集成。
- 源生成宿主绑定；基础类型和手写 descriptor 也提供完整 AOT 路径。受控反射适配只有通过 AOT/trim 验证才进入正式运行时交付。
- 定时器、`fetch`、URL、流、受控文件访问等宿主环境能力；可选安装不等于豁免 AOT 要求。
- 后续经过验证的构建期预编译、调试协议、TypeScript 工具集成；运行时 IL 后端不在当前主路线。

### 不作为首版承诺

- 浏览器 DOM、完整 Node.js/npm 运行环境。
- TypeScript 类型检查或完整 TypeScript 编译器。
- 全量 ECMA-402 / Intl、Temporal、所有最新提案。
- 与 V8 的所有扩展、错误文案、堆快照格式完全兼容。
- 同进程内对恶意代码提供 OS 级 CPU/RSS 硬隔离。
- 单个有状态引擎的并行执行、SharedArrayBuffer/Atomics 多线程模型。
- 首版公开持久化字节码格式或直接载入不可信二进制；运行时 JS→IL/JIT 不作为当前交付或性能达标的依赖。

## 5. 推荐的架构方向

```text
C# 应用
  ├─ 简单入口：Evaluate / SetValue / SetFunction
  ├─ 高性能入口：Compile → Load → GetFunction → Invoke
  └─ 插件入口：DTO/JSON → 隔离执行 → DTO/JSON
                         │
              宿主绑定 / 模块加载 / 执行策略
                         │
        解析器适配 → 自有中间表示 → 不可变字节码
                                          │
                   每引擎私有 Realm / 帧 / IC / jobs
                                          │
                         寄存器字节码解释器
                                          │
                           CLR GC 与 BCL
```

首版优先验证以下组合，而不是直接实现一套大型 JIT：

- **成熟 parser + 自有字节码编译器**：候选 Acornima，语法正确性与工程成本优先；经过适配后不向公共 API 泄露其 AST。
- **寄存器 VM**：减少动态 AST 分派；是否优于其他布局必须在 CLR 上实测。
- **GC 安全的 tagged value、shape/slot 与 inline cache**：让常见数字、属性读写、函数调用走短路径。
- **不可变代码共享，活对象与反馈私有**：并行依靠多个独立引擎，不共享全局变量和模块状态。
- **NativeAOT 强制兼容**：发布后仍可将构建时未知的新 JS 编译为字节码并执行；核心功能、绑定与数据转换不能依赖运行时发 IL 或静默反射回退。

详见 [架构](02-architecture.md)。

## 6. API 分成三层，但不制造三套引擎

### A. 简单调用

目标是用少量代码完成注册和求值：

```csharp
using var engine = new JsEngine();
engine.SetValue("price", 100.0);
engine.SetFunction("tax", (double amount) => amount * 0.13);

double total = engine.Evaluate("price + tax(price)").AsNumber();
```

### B. 可复用、高性能调用

- `JsCompiler` 产生不可变 `JsScript` / `JsModule`。
- `JsEngine` 是单个有状态执行实例，不是全局线程安全编译服务。
- `JsModuleInstance` 和 `JsFunction` 属于具体引擎。
- 缓存编译产物和函数句柄，避免重复解析、名字查找、`params object[]` 和反射。

### C. 插件生产入口

- 输入输出支持源生成 DTO 映射或 JSON。
- 统一涵盖参数转换、执行、Promise 调度、结果转换的执行预算。
- 默认每次调用使用新 Realm；有状态会话必须显式选择。
- 在归还租约前输出普通 .NET 数据，不让 JS 对象句柄逃逸。

完整示例与生命周期契约见 [公共 API](03-public-api.md)。

## 7. 正确性、安全和性能的优先关系

1. **不改变 JS 语义来隐藏性能成本。** 冻结内建对象属于显式 Hardened profile，不冒充标准默认行为。
2. **不把复用等同于隔离。** 清空调用缓存不等于清除全局、闭包、模块单例和异步任务。
3. **不把逻辑额度等同于进程内存硬限。** CLR 堆、宿主回调、共享缓存另有成本。
4. **不拿未实现的功能换更漂亮的比较。** 基准必须公开共同功能、隔离策略和安全选项。
5. **不把设计目标写成成绩。** 本轮没有 Jaunt 实现，也没有运行任何跨引擎性能基准。
6. **AOT 是架构前提，不是最后补做的兼容层。** 每阶段承诺的运行时能力都须完成 NativeAOT 发布后实际运行验证，不能只在 CoreCLR 成立；普通 CoreCLR 部署仍然支持。

推荐先建立“正确实现 + 可测基线”，再按真实瓶颈投入优化；高性能不是堆叠 `unsafe`、SIMD、JIT 等名词。

## 8. 竞争位置

MoeJS 给出了插件工作负载优先的产品范式；Jint 是必须比较的成熟托管入口；ClearScript/V8 是原生集成路线；QuickJS 展示小型引擎的工程取舍。

本轮还发现 **Okojo** 已采用纯托管寄存器 VM、共享代码/私有 Realm 数据、AOT 与源生成绑定等思路。因此这些机制不是 Jaunt 独有卖点。真正的差异化需要以以下结果证明：

- .NET 8/10/11 上一致、容易使用的 API；
- 有代表性的 .NET 插件端到端成本，而非单一微基准；
- 明确而可信的隔离、异步与数据所有权契约；
- 可追溯的兼容性与回归验证。

详见 [竞品调研](01-research.md)。
